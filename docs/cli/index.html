Server edition · Linux & macOS

SSH tunnels that stay up on your server, managed from a browser.

Tunnel Pilot CLI is Tunnel Pilot without the window. A daemon holds your ssh -L forwards open and reconnects them when they drop; you manage it from the terminal or from the desktop app’s interface in your browser. For servers, homelabs, a Raspberry Pi, CI boxes.

How it works

One daemon, two ways in

The daemon owns the tunnels. The terminal and the browser are two front ends to the same state, so a forward you add in one shows up in the other.

The daemon

tunnel-pilot-cli service install

Keeps every forward open with SSH keep-alive and reconnects with backoff when one drops. Runs as a systemd service (a user unit, or a system unit as root) or a launchd agent on macOS.

The terminal

tunnel-pilot-cli list --json

add, edit, remove, connect, disconnect, status — every command takes --json, so scripts, cron jobs and CI can drive it.

The web UI

http://127.0.0.1:1855

The same interface as the desktop app — groups, tags, live stats, logs, backup, the ⌘K palette — behind an admin password. Optional: leave out --web and it isn’t served.

Install

One command in, one command out

Linux x86_64 and aarch64 (a static binary that runs on any distro) and macOS. Not Windows — use the desktop app there.

Install
curl -fsSL https://kalfian.github.io/tunnel-pilot/cli/install.sh | bash

Installs tunnel-pilot-cli to ~/.local/bin, or to /usr/local/bin as root or with -s -- --system. The download is SHA-256 verified and refused if the checksum is missing or wrong.

Uninstall
curl -fsSL https://kalfian.github.io/tunnel-pilot/cli/uninstall.sh | bash

Stops and removes the service and the binary, and keeps your config. Add -s -- --purge to also delete the config, the web admin password and stored passwords.

You’re on Windows

This edition doesn’t run on Windows. The desktop app has the same features, in the tray.

Quick start

From install to a running web UI

Set a password, install the service, open the browser. The service starts at boot and the web UI listens on localhost until you choose otherwise.

Terminal only? Leave out --web; the daemon runs without the web UI and every action is a command.

  1. 1

    Set the web admin password

    Prompted with echo off and stored as an argon2id hash. Setting it again signs everyone out.

    tunnel-pilot-cli web set-password
  2. 2

    Install the service with the web UI

    The web UI is on http://127.0.0.1:1855 — on the server itself, or from your machine through an SSH tunnel.

    tunnel-pilot-cli service install --web
  3. 3

    Reach it from other machines (optional)

    Listens on every interface at http://<server-ip>:1855. Plain HTTP — put HTTPS in front before you rely on it.

    tunnel-pilot-cli service install --web --bind 0.0.0.0
  4. 4

    Add forwards — in the browser or here

    Key auth shown; --password prompts instead and never takes the password as a flag value. Then list, connect, disconnect and status, all with --json.

    tunnel-pilot-cli add prod-db \
  --ssh deploy@bastion.example.com \
  --forward 5432:db.internal:5432 \
  --identity ~/.ssh/id_ed25519
Web UI security

Locked by default. Bring your own HTTPS.

The web UI controls SSH access to your network, so it is built to be safe on localhost and explicit about what it doesn’t do.

  • Login always required — one admin password, stored as an argon2id hash.
  • Session cookie — HttpOnly and SameSite=Strict.
  • CSRF protection — a request’s Origin must match the host it was sent to.
  • Login rate limiting per client (IPv6 per /64), with a lockout that backs off, and a cap on concurrent password checks.
  • Host allowlist — only IP addresses, localhost and names you add with --public-host are answered, which blocks DNS rebinding.
  • Connection limits — slow or stalled clients are dropped and open connections are capped.
  • Pinned SSH host keys — each tunnel pins its server’s key on first connect (and honours ~/.ssh/known_hosts); a changed key is refused until you verify and trust it.
  • Not as root — a root service with the web UI is refused unless you pass --allow-root; install it as a normal user.
  • Strict Content-Security-Policy — its own scripts only, no framing.
  • Localhost unless you say otherwise — binds 127.0.0.1; 0.0.0.0 only with --bind.

No built-in TLS

The web UI speaks plain HTTP, and warns on every page when it is reached that way from another machine. Before you expose it beyond localhost, put an HTTPS reverse proxy in front of it — or skip exposing it and reach it through an SSH tunnel.

Caddyfile 
tunnels.example.com {
    reverse_proxy 127.0.0.1:1855
}
then run the daemon for that name 
tunnel-pilot-cli service install --web \
  --public-host tunnels.example.com --trust-proxy

Caddy gets a certificate for the domain automatically and passes the Host header, the X-Forwarded-* headers and WebSocket upgrades through. Keep the daemon on the default 127.0.0.1 bind. --public-host allows the domain name (other names are refused, which blocks DNS rebinding); --trust-proxy makes the rate limit and the secure cookie use the client address and HTTPS the proxy reports.

inside your HTTPS server { } block 
location / {
    proxy_pass http://127.0.0.1:1855;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
then run the daemon for that name 
tunnel-pilot-cli service install --web \
  --public-host tunnels.example.com --trust-proxy

proxy_set_header Host $host; is required: the CSRF check compares the browser’s Origin with the host, and the host must be one you allowed with --public-host. The X-Forwarded-* lines feed --trust-proxy; the Upgrade and Connection headers keep the live status stream, a WebSocket, working.

on your own machine 
ssh -N -L 1855:127.0.0.1:1855 you@your-server

Then open http://127.0.0.1:1855 locally. Nothing is exposed and SSH encrypts the traffic. Replace you@your-server with your login — or save it as a forward in Tunnel Pilot desktop.

Same app, different delivery

Everything the desktop app does

One codebase, identical features. Only the delivery differs: no tray and no window — a service, a terminal and a browser instead.

  • Local port forwards — ssh -L with a password or an identity file.
  • Groups and tags to sort forwards by environment.
  • Auto-reconnect with SSH keep-alive liveness.
  • Live stats per tunnel — connections, traffic, latency, uptime.
  • Activity log with level filter and search.
  • Backup export and import; backups never contain passwords.
  • ⌘K command palette in the web UI.
  • Passwords in the OS keychain, or a 0600 file where there is none.
  • Free and open source, MIT License.

FAQ

Common questions

Does it run on Windows?

No — Tunnel Pilot CLI is built for Linux x86_64, Linux aarch64 and macOS. On Windows, use the desktop app: the same features in a tray app with a window.

Can I install it next to the desktop app?

Yes. They are separate products with separate config, so they install side by side. To move forwards from one to the other, export a backup in one and import it in the other. Backups never contain passwords, so set those again afterwards.

How do I serve the web UI over HTTPS?

It has no built-in TLS. Put an HTTPS reverse proxy such as Caddy or nginx in front of 127.0.0.1:1855, or keep the default localhost bind and reach it through an SSH tunnel. Start the daemon with --public-host <your domain> --trust-proxy. With nginx, pass proxy_set_header Host $host;, the X-Forwarded-* headers and the WebSocket Upgrade and Connection headers. Examples are in Web UI security.

Do I need the web UI?

No. Leave out --web and the daemon runs without it. Every action is also a terminal command — add, edit, remove, list, connect, disconnect, status — all with --json output.

Where are SSH passwords stored?

In the OS keychain when one is available. On a server without a keychain they go to a separate file readable only by its owner (mode 0600), and the web UI shows a notice saying so. The web UI admin password is stored as an argon2id hash.
